I ignored Claude Code's `/voice` command for weeks. Talking to a terminal sounded like a demo feature — the kind of thing that looks great on stage and gathers dust in real work. Then I threw my back out, ended up working half-reclined on a couch with the laptop across the room, and suddenly "drive Claude Code without touching the keyboard" went from gimmick to necessity.

A week later, I'm keeping it — not for everything, but for a specific and surprisingly common slice of work where speaking genuinely beats typing. Here's the honest report: how it works, where it earned its place, and where it's still worse than just typing.

## How /voice works

You activate it by typing `/voice` in a session. The default interaction is **push-to-talk** — hold `Space`, speak, release, and Claude processes what you said. That push-to-talk default is the right call; open-mic voice interfaces pick up every "um," cough, and side conversation, and push-to-talk keeps you in control of exactly what the model hears.

Three things make it more than a novelty:

- **It runs on any Claude tier** — Opus, Sonnet, or Haiku — and you can **switch models mid-conversation** from the picker. So you can talk to a cheap model for quick back-and-forth and jump to [Opus 5](/blog/claude-opus-5-claude-code-developer-review) the moment the problem gets hard, without breaking the voice flow.
- **It reaches your connected tools.** Voice isn't a sandboxed chat — it can drive the [MCP tools you've wired up](/blog/developer-mcp-stack-multi-tool-workflow-guide), like Gmail and Slack. "Summarize the last message in the incidents channel and draft a reply" works out loud.
- **It speaks many more languages** than the initial release, so non-English speakers aren't stuck narrating code in a second language.

## Where talking actually wins

I was surprised by how quickly a mental model formed for *when* voice is better. It's not about laziness — it's about the shape of the interaction.

**Long, exploratory framing.** When I'm starting a task and need to explain a lot of context — "here's what this module does, here's the bug I think exists, here's the three places I'd look" — I talk faster than I type, and I ramble in a more *complete* way. Typing makes me terse; speaking makes me thorough. For handing an agent a rich problem statement, that thoroughness is exactly what produces a better plan. Good [context engineering](/blog/context-engineering-claude-code-guide) is mostly about giving the model enough to work with, and I give more when I'm talking.

**Reviewing and redirecting while away from the keyboard.** This is the killer use case and the one that kept me. When Claude is executing a long task, I don't need to type — I need to *watch and course-correct*. "No, use the existing helper instead of writing a new one." "Stop, that's the wrong file." Speaking those redirects while I lean back and read is genuinely more comfortable than hunching forward to type them. It turns supervising an agent into something closer to pairing with a junior over your shoulder.

**Accessibility, and it's not a footnote.** For anyone with RSI, a wrist injury, or any condition that makes sustained typing painful, voice isn't a convenience — it's access. I got a temporary, involuntary taste of that this week, and it reframed the feature entirely. The people for whom this is transformative aren't chasing novelty; they're getting their tools back.

## Where typing still wins, decisively

I'll be equally blunt about the limits, because the demos won't be.

**Anything involving exact syntax.** You cannot usefully dictate a regex, a file path with weird characters, or a precise API signature. The model guesses at what you mumbled and gets it subtly wrong, and now you're correcting transcription errors instead of writing code. For anything where the exact characters matter, type it.

**Noisy or shared environments.** Push-to-talk helps, but an open office or a coffee shop makes voice both unreliable (background noise corrupts transcription) and antisocial (nobody wants to hear you narrate a refactor). This is a heads-down-at-home feature far more than an open-plan-office one.

**Fast, precise iteration.** When I'm in a tight loop — small edit, check, small edit — typing's precision and speed win. Voice has just enough latency (speak, release, transcribe, process) that it breaks the rhythm of rapid-fire iteration. Voice is for the expansive parts of the work, not the staccato ones.

## How I actually use it

The pattern that settled out after a week: **voice for the bookends, keyboard for the middle.** I talk to set up a task — the long, context-rich framing where thoroughness matters — and I talk to supervise and redirect while it runs and I'm reading rather than typing. But the moment I'm doing precise, syntax-heavy, fast-iteration work, I'm back on the keyboard where I belong.

It pairs especially well with the more autonomous, hands-off ways of running Claude Code. If you're already [dispatching agents to work remotely](/blog/claude-code-remote-control-dispatch-guide) and checking in on them, voice is a natural control surface for that check-in — you're supervising, not typing, which is exactly what voice is good at.

## The bottom line

`/voice` isn't going to replace your keyboard, and anyone who tells you it will is selling something. But it's also not the gimmick I assumed. It's a genuinely better interface for a real slice of agentic work — the expansive, context-heavy framing at the start of a task and the watch-and-redirect supervision while it runs — and it's real accessibility for people who need it. Type `/voice`, hold `Space`, and use it for the parts of the job where you'd rather be leaning back reading than hunched forward typing. Keep the keyboard for the syntax and the fast loops. Used that way, it's a legitimately useful addition to how you drive an agent — just don't expect it to dictate your regexes.
